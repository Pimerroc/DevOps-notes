### Процессы внутри контейнера

Контейнер не ограничивается обязательным запуском только одного процесса. В нём могут находиться несколько процессов. Проблема возникает с процессами, которые завершаются, но не были корректно «собраны» родителем с помощью `wait()`.

Особенно это важно для **PID 1** внутри контейнера. Если процесс становится родителем дочернего процесса, о существовании которого он не знает, завершившиеся процессы могут оставаться в системе.

Для решения этой проблемы Docker предоставляет:

```
docker run --init ...
```

В этом случае Docker запускает простой процесс инициализации как PID 1. Он выполняет роль родителя и забирает завершившиеся дочерние процессы.

Если же внутри контейнера необходимо управлять несколькими службами или группами задач, книга предлагает использовать менеджер процессов, например **Supervisor (**`**supervisord**`**)**, который занимается запуском и мониторингом этих процессов.

### LXC

**LXC** — более старая система контейнеризации. Первые версии Docker фактически использовали LXC. В отличие от Docker, LXC требует больше ручной настройки.

Например, необходимо самостоятельно настраивать сетевой интерфейс контейнера и сопоставление идентификаторов пользователей. Изначально LXC задумывался как средство запуска внутри контейнера практически полноценной Linux-системы, включая систему инициализации.

Поэтому LXC в книге описывается как более **гибкая**, но одновременно более требовательная к ручной настройке система. Например, overlay-файловая система, используемая Docker, в LXC по умолчанию отсутствует, хотя её можно добавить. Для управления LXC существует **LXD**, который упрощает работу с сетью и образами и предоставляет REST API.

### Kubernetes

Когда контейнеров становится много, проблема уже состоит не только в создании отдельного контейнера. Необходимо:

- определять машины, на которых можно запускать контейнеры;
- запускать, отслеживать и перезапускать их;
- настраивать их запуск;
- организовывать сеть;
- обновлять образы и уже работающие контейнеры.

Для решения таких задач используется **Kubernetes**.

В книге Kubernetes описывается как клиент-серверная система:

- **серверная сторона** включает машины, на которых могут работать контейнеры;
- **клиентская сторона** в основном представлена инструментами командной строки, с помощью которых запускаются и управляются группы контейнеров.

Kubernetes может запускать Docker-образы. Для локального изучения Kubernetes книга упоминает **Minikube**, который устанавливает виртуальную машину с кластером Kubernetes.

### Проблемы контейнеризации

Контейнеры не устраняют необходимость в инфраструктуре. Для их запуска всё равно нужны полноценные Linux-машины — физические или виртуальные. Эту инфраструктуру необходимо обслуживать, а при использовании готовой контейнерной платформы фактически оплачивается её обслуживание поставщиком.

Кроме того, контейнер должен содержать всё необходимое пользовательскому приложению, включая библиотеки Linux, поэтому множество контейнеров также может занимать значительное место в хранилище.

Другой вопрос связан с безопасностью готовых образов: использование образа из публичного репозитория означает доверие его содержимому. Поэтому книга отдельно обращает внимание на риск безопасности и рекомендует учитывать версионность базовых образов. При использовании последнего выпуска образа изменения могут повлиять на приложение, поэтому лучше фиксировать конкретный тег версии.

Таким образом:

```
Виртуальная машина
    ↓
полноценная гостевая ОС + собственное ядро
    ↓
сильная изоляция, но большие затраты

Контейнер
    ↓
изолированное окружение процессов
    ↓
общее ядро хоста
    ↓
меньше накладных расходов, но нужна общая инфраструктура
```

Наконец, книга рассматривает ещё один вид изоляции — **виртуализацию времени исполнения**. Она применяется не ко всей системе, а к отдельному приложению. Например, разные Python-программы могут требовать несовместимые версии пакетов. Для этого можно создать отдельное виртуальное окружение:

```
python3 -m venv test-venv
. test-venv/bin/activate
```

После активации используется отдельная среда Python и отдельная библиотека пакетов `test-venv/lib`, а выход выполняется командой:

```
deactivate
```

Таким образом, виртуальное окружение Python изолирует зависимости приложения, но не является виртуальной машиной или системным контейнером.
