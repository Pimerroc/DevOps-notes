## 7.1 Служба имен доменов DNS (стр. 684–704)

### 7.1.1 История и общие сведения (стр. 685)

- В ARPANET имена и IP-адреса всех хостов хранились в файле `hosts.txt`; хосты скачивали его каждую ночь. DNS разработана в 1983 г.; описана в RFC 1034, RFC 1035, RFC 2181 (стр. 685).

> DNS представляет собой сочетание иерархической схемы именования с распределенной базой данных, реализующей эту схему (стр. 685).

### 7.1.2 Процесс поиска DNS (стр. 685–688)

- Приложение вызывает библиотечную процедуру (gethostbyname) — «оконечный распознаватель» (stub resolver); тот шлёт запрос локальному рекурсивному распознавателю; запрос и ответ передаются UDP-пакетами (стр. 685).
- Сервер, отвечающий за часть иерархии, — **авторитетный сервер имен** (authoritative name server). Локальный распознаватель возвращает только полные ответы; корневые (и последующие) серверы рекурсию не выполняют — отдают частичный ответ, процесс продолжают итеративные запросы. Каждый запрос несёт 16-битный идентификатор транзакции, копируемый в ответ (стр. 686).
- Все ответы (включая частичные) кэшируются; кэшированные ответы неавторитетны — каждая запись содержит поле Time_to_live (сутки для стабильных данных, секунды–минуты для изменчивых) (стр. 686–687).
- **QNAME-минимизация**: локальный распознаватель посылает авторитетному серверу только обрабатываемую им часть имени (RFC 7816) (стр. 687).
- Исторически транспорт — UDP; тренд к TCP открыл путь DNS-over-TLS (**DoT**) и DNS-over-HTTPS (**DoH**); при тайм-ауте запрос повторяется к другому серверу домена (стр. 687).

### 7.1.3 Пространство имен и иерархия DNS (стр. 688–692)

- Иерархию разрабатывает ICANN (создана в 1998 г.); >250 доменов верхнего уровня (ДВУ); дерево пространства имен — илл. 7.1 (стр. 688).
- Типы ДВУ: родовые (рДВУ, gTLD) и национальные (нДВУ, ccTLD; по ISO 3166 — один на государство); интернационализированные имена — с 2010 г. (стр. 688).
- Исходные рДВУ (илл. 7.2, стр. 689): com, edu, gov, mil, net, org — 1985 (ограниченные: edu, gov, mil); int — 1988; aero, biz, coop — 2001; info, museum, name, pro — 2002; cat, jobs, mobi, tel, travel — 2005; xxx — 2010.
- В 2011 г. было 22 рДВУ; ICANN сняла ограничения (заявки с 2012 г., ~$200 000); к 2020 г. — >1200 рДВУ; первые нелатинские — июль 2013 г. (стр. 689–690).
- ДВУ управляют **реестры** (registries; для com — Verisign), продажу ведут **регистраторы** (registrars: GoDaddy, NameCheap) (илл. 7.3, стр. 690).
- **FQDN** — полностью квалифицированное доменное имя; абсолютное имя оканчивается точкой (стр. 690–691).
- Имена нечувствительны к регистру; компонент — до 63 символов, полное имя — до 255; регистр используется для защиты от отравления кэша — 0x20-кодирование (стр. 691, 693–694).

### 7.1.4 DNS-запросы и DNS-ответы (стр. 692–699)

- Самый частый запрос — A-запись; **DNSBL** — чёрные списки IP-адресов спамеров: адрес 127.0.0.2 проверяется запросом `2.0.0.127.pbl.spamhaus.org`; при отсутствии в списке — ответ NXDOMAIN («no such domain») (стр. 692).
- **EDNS Client Subnet**: локальный распознаватель передаёт авторитетному серверу IP-подсеть клиента для выбора ближайшей реплики (Google 8.8.8.8 и CloudFlare 1.1.1.1 сами местоположение не раскрывают) (стр. 692–693).
- 0x20-кодирование: случайный регистр символов QNAME служит дополнительными битами к 16-битному идентификатору (защита от атаки Каминского) (стр. 693–694).
- Ресурсная запись (ASCII-вид): `Domain_name Time_to_live Class Type Value`; Class = IN для интернета (стр. 694). Типы записей (илл. 7.4, стр. 695):

| Тип | Значение | Value |
|---|---|---|
| SOA (Start Of Authority) | начальная запись зоны | параметры зоны |
| A (Address) | IPv4-адрес хоста | 32-битное целое |
| AAAA | IPv6-адрес хоста | 128-битное целое |
| MX (mail exchanger) | обмен почтой | приоритет приёма почты |
| NS | сервер имен | имя сервера для домена |
| CNAME | каноническое имя | имя домена (псевдоним) |
| PTR | указатель | псевдоним IP-адреса (обратный просмотр) |
| SPF | правила отправки почты | правила в текстовом виде |
| SRV | служба | хост, предоставляющий службу |
| TXT | текст | описательный ASCII-текст |

- Пример CNAME: `www.cs.uchicago.edu 120 IN CNAME hnd.cs.uchicago.edu`; записи TXT сегодня обычно кодируют SPF-информацию (стр. 696).
- **DNSSEC** (RFC 3833): цифровая подпись набора записей ресурсов (RRSET) закрытым ключом сервера; записи **RRSIG** (подпись) и **DNSKEY** (открытый ключ); открытый ключ подписан родительским сервером — достаточно доверять корню (стр. 696–697).
- Файл DNS-зоны cs.vu.nl (илл. 7.5, стр. 697–698): SOA (TTL 86400); MX 1 zephyr, 2 top; NS star; A: star 130.37.56.205, zephyr 130.37.20.10, top 130.37.20.11; CNAME www и ftp → flits; flits — два A (130.37.16.112, 192.31.231.165) и MX 1 flits, 2 zephyr, 3 top (илл. 7.5).
- Пространство имен делится на непересекающиеся **зоны**; границы задаёт администратор зоны (илл. 7.6, стр. 698–699).

### 7.1.5 Разрешение имен (стр. 699–701)

- Зона: один основной сервер имен (берёт данные с диска) + второстепенные (получают с основного); часть серверов может располагаться вне зоны; авторитетная запись отличается от кэшируемой (стр. 699).
- Поиск flits.cs.vu.nl → cs.uchicago.edu за 10 шагов через корневой сервер, сервер edu, сервер uchicago.edu и сервер cs.uchicago.edu (илл. 7.7, стр. 700).
- **13 корневых серверов**: a-root-servers.net … m.root-servers.net; активно реплицируются, доступ через anycast-маршрутизацию (стр. 700).

### 7.1.6 Практическое ознакомление с DNS (стр. 701)

```
dig ns @a.edu-servers.net cs.uchicago.edu
```
Организации используют обычно 5–6 серверов имен (стр. 701).

### 7.1.7 DNS и конфиденциальность (стр. 701–704)

- Незашифрованный DNS виден на пути: запросы раскрывают посещённые сайты; DNS-трафик IoT-устройств однозначно идентифицирует устройства умного дома (стр. 701–702). Google, CloudFlare предлагают шифруемые рекурсивные распознаватели; Mozilla внедряет DoH в браузер (стр. 702).
- **Trusted Recursive Resolver (TRR)** — доверенные рекурсивные распознаватели поверх DoT/DoH (стр. 702–703).
- Оператор распознавателя всё равно видит запросы; альтернативы — **oblivious DNS (ODNS/ODoH)**: оконечный распознаватель шифрует запрос, авторитетный сервер дешифрует, не зная клиента (илл. 7.8, стр. 703).

### 7.1.8 Разногласия по поводу способов именования (стр. 704)

- Спорные вопросы ICANN: домен xxx (суды), ограничения домена pro; Тувалу сдала домен tv в аренду за $50 млн; регистрация имён для перепродажи — киберсквоттинг (cybersquatting) (стр. 704).

## 7.2 Электронная почта (стр. 704–725)

### Архитектура и службы (стр. 706–708)

- Две подсистемы: **пользовательские агенты** (user agent) и **агенты передачи сообщений** (message transfer agent, почтовые серверы); шаги: подача (mail submission) → передача (SMTP) → окончательная доставка (илл. 7.9, стр. 706); 9 из 10 писем — спам (стр. 705).
- SMTP: RFC 821 → текущая редакция RFC 5321; отчёты о доставке, списки рассылки (стр. 707). Конверт отделён от сообщения: сообщение = заголовок + тело (илл. 7.10, стр. 707–708).

### Пользовательский агент (стр. 708–710)

Gmail, Outlook, Thunderbird, Apple Mail; старые текстовые — Elm, mh, Pine. Размещение сообщения (message disposition): удалить, ответить, переслать; спам генерируется ботнетами (стр. 710).

### Форматы сообщений (стр. 710–716)

- RFC 5322 (переработка RFC 822): конверт, поля заголовка, пустая строка, тело (стр. 710–711).
- Заголовки (илл. 7.12, стр. 711): To:, Cc:, Bcc:, From: (обязательное), Sender:, Received:, Return-Path:; дополнительные: Date:, Reply-To:, Message-Id:, In-Reply-To:, References:, Subject:; пользовательские — с X- (стр. 713).
- **MIME** (Multipurpose Internet Mail Extensions; RFC 2045): структура тела и кодирование не-ASCII (стр. 713). Пять заголовков MIME (илл. 7.14, стр. 714): MIME-Version:, Content-Description:, Content-Id:, Content-Transfer-Encoding:, Content-Type:.
- Кодировки передачи: 7-битный ASCII, 8-битный, binary, **base64** (24 бита → 4 символа по 6 бит) (стр. 714–715).
- MIME-типы (илл. 7.15, стр. 716): text, image, audio, video, font, model, application, message, multipart; список ведёт IANA.

### Пересылка сообщений (стр. 716–721)

- SMTP: TCP, порт 25 получателя; ASCII-протокол (стр. 716–717).
- Диалог (илл. 7.16, стр. 717–718): S: 220 → C: HELO → MAIL FROM → RCPT TO (по одному на получателя) → DATA (S: 354, конец — точка в отдельной строке) → S: 250 → QUIT.
- Ограничения SMTP: нет аутентификации (подделка FROM), только ASCII, без шифрования (стр. 717–718).
- **ESMTP**: EHLO вместо HELO; расширения (илл. 7.17, стр. 719): AUTH, BINARYMIME, CHUNKING, SIZE, STARTTLS, UTF8SMTP.
- Подача почты: SMTP + AUTH, часто порт **587** (RFC 4409); выбор сервера получателя — по MX-записям DNS (стр. 720–721).

### Окончательная доставка (стр. 721–725)

- SMTP — push-протокол: не годится, если агент отключён (стр. 722).
- **IMAP** (RFC 3501), порт **143**; команды (илл. 7.18, стр. 723): CAPABILITY, STARTTLS, LOGIN, AUTHENTICATE, SELECT, FETCH, SEARCH, STORE, COPY, EXPUNGE и др.; mailbox = папка (стр. 722).
- **POP3** (RFC 1939): проще, почта скачивается на клиент и не остаётся на сервере (стр. 724).
- Веб-почта: пользовательский агент = веб-интерфейс; приём по-прежнему SMTP (стр. 724).

## 7.3 Всемирная паутина (стр. 725–758)

### Архитектура (стр. 726–735)

- WWW создана в 1989 г. в CERN Тимом Бернерс-Ли; Mosaic — февраль 1993 г.; Amazon (1994), eBay (1995), Google (1998), Facebook (2004); W3C основан в 1994 г. (стр. 725–726).
- Статичная страница — всегда одинаковый документ; динамическая — создаётся программой (стр. 728).
- **URL** = схема (протокол) + DNS-имя хоста + путь (стр. 729). Шаги загрузки https://fcc.gov/ (илл. 7.19): DNS-запрос → IP → TCP на порт 443 (HTTPS; 80 — HTTP) → HTTPS-запрос → ответ → загрузка встроенных объектов → отображение (стр. 729–730).
- Схемы URL (илл. 7.21, стр. 732): http, https, ftp, file, mailto, rtsp, sip, about.
- Веб-сервер: принять TCP → получить путь → взять файл → отправить → разорвать (стр. 733); многопоточный сервер (илл. 7.22, стр. 734); интерфейсный веб-сервер — **обратный прокси** (reverse proxy) (стр. 734–735).

### Статичные и динамические объекты (стр. 735–740)

- **HTML** — язык разметки; таблицы стилей — **CSS** (стр. 735–736).
- Серверная генерация: **CGI** (RFC 3875) — программы в cgi-bin; **PHP** — скрипты внутри страницы (стр. 738–739).
- Клиентская генерация: тег `<script>` (HTML 4.0); HTML5 — `<video>`, `<audio>`, `<canvas>`; JavaScript выполняется в браузере; `<canvas>`-отпечаток — отслеживание без cookies (стр. 739–740).

### HTTP и HTTPS (стр. 740–753)

- HTTP — RFC 2616; HTTPS = HTTP поверх TLS; HTTP/3 работает поверх UDP (стр. 740–741).
- Методы (илл. 7.25, стр. 742): GET, HEAD, POST, PUT, DELETE, TRACE, CONNECT, OPTIONS. Пример: `GET filename HTTP/1.1`.
- Коды состояния (илл. 7.26, стр. 743):

| Код | Группа | Примеры |
|---|---|---|
| 1xx | информация | 100 |
| 2xx | успех | 200, 204 |
| 3xx | перенаправление | 301 (перемещена), 304 (кэш актуален) |
| 4xx | ошибка клиента | 403, 404 |
| 5xx | ошибка сервера | 500, 503 |

- Заголовки (илл. 7.27, стр. 744): запрос — User-Agent, Accept, If-Modified-Since, If-None-Match, Host (обязателен), Authorization, Referer, Cookie; ответ — Set-Cookie, Server, Content-Encoding, Content-Type, Content-Length, Location, Expires; оба — Date, Range, Cache-Control, ETag, Upgrade (стр. 743–744).
- **Cookies** (RFC 2109): сервер шлёт Set-Cookie, клиент возвращает в заголовке Cookie (стр. 745).
- Кэширование: Expires или conditional GET (If-Modified-Since / If-None-Match) (илл. 7.28, стр. 747–748).
- HTTP/1.0 — соединение на запрос; HTTP/1.1 — **постоянные соединения**; закрытие после простоя ~60 с (илл. 7.29, стр. 748–750).
- **HTTP/2** (RFC 7540, май 2015; база — SPDY): двоичное кодирование, фреймы с идентификаторами, мультиплексирование в одном TCP-соединении, сжатие заголовков, произвольный порядок ответов, server push; шифрование требуют все современные браузеры (илл. 7.30, стр. 750–752).
- **HTTP/3**: транспорт QUIC (UDP); установка без дополнительных кругов; применяется только с HTTPS (стр. 752–753).

### Конфиденциальность в интернете (стр. 753–758)

- Cookies собственные vs сторонние; политика одного источника (same-origin); межсайтовое отслеживание (cross-site tracking) (стр. 753–754).
- Отслеживание устройств: cookies, объекты HTML5, JavaScript, canvas fingerprinting; синхронизация cookie-файлов (cookie syncing) (стр. 755–758).

## 7.4 Потоковая передача аудио и видео (стр. 758–785)

- Мультимедиа — непрерывные данные: критичны задержка и джиттер; голос — 64 Кбит/с; 4K ~8 Мбит/с ≈ 7 ГБайт на 2-часовой фильм (стр. 758–759).

### Цифровой звук (стр. 759–762)

- Слух: 20–20 000 Гц; громкость в дБ; 0 дБ — порог слышимости, болевой порог ~120 дБ (стр. 760).
- Оцифровка: частота дискретизации ≥ 2f по Найквисту (стр. 760). Форматы: **MP3** (MPEG-1 audio layer 3), **AAC** — замена MP3 в MPEG-4 (стр. 761–762). Перцепционное кодирование: частотное и временное маскирование (стр. 762).

### Цифровое видео (стр. 762–766)

- 24 бита/пиксель; разрешения: 1280×720 (720p), 1920×1080 (1080p), 3840×2160 (4K), 7680×4320 (8K); PAL 25 кадр/с, NTSC 29,97 (стр. 763). Без сжатия PAL 720p — 553 Мбит/с (стр. 763).
- **JPEG**: RGB → яркость/цветность, блоки 8×8, дискретное косинусное преобразование (стр. 764).
- **MPEG**: I-кадры (независимые), P-кадры (отличия от предыдущего), B-кадры (отличия от следующего) (илл. 7.32); MPEG-4 = H.264, следующая версия — H.265 (стр. 764–765).

### Потоковая передача сохранённых медиафайлов (стр. 766–774)

- Пять задач медиаплеера: интерфейс, обработка ошибок, декомпрессия, устранение джиттера, дешифрование (стр. 767).
- Транспорт: TCP (HTTP) — надёжно, но тайм-ауты; UDP (RTP) — потери компенсируют FEC и выборочный повтор I-кадров; интервал I-кадров 1–5 с (стр. 767–768).
- Буфер воспроизведения 5–30 с; YouTube, Netflix, Hulu используют TCP (илл. 7.34, стр. 768–770).
- **DASH** (Dynamic Adaptive Streaming over HTTP): фильм в 7 разрешениях × 6 частот кадров = 42 варианта, сегменты по 10 с ⇒ 42 × 540 = 22 680 файлов для 90-минутного фильма; манифест **MPD**; плеер выбирает качество по пропускной способности (илл. 7.35, стр. 770–772).
- **HLS** (Apple, RFC 8216): проприетарный, кодеки Apple; DASH инвариантен к кодеку; YouTube и Netflix используют DASH (стр. 773).

### Потоковая передача в реальном времени (стр. 774–785)

- IP-телефония: задержка ≤ 150 мс в одном направлении (до 400 мс) (стр. 775). Сиэтл–Амстердам: 40 мс распространения; сэмплы блоками по 20 мс ⇒ суммарно 62 мс (стр. 775–776).
- **H.323** (МСЭ, 1996): терминалы, шлюз, привратник (gatekeeper) (илл. 7.36, стр. 778); стек: аудио G.7xx (обязателен G.711 — 64 Кбит/с), сигнализация Q.931 (TCP), канал **RAS** (H.225, UDP), данные RTP/RTCP (стр. 779).
- **SIP** (RFC 3261): текстовый протокол по модели HTTP; методы (илл. 7.39): INVITE, ACK, BYE, OPTIONS, CANCEL, REGISTER; адреса `sip:ilse@cs.university.edu`; коды ответов как в HTTP (стр. 781–782).
- H.323 vs SIP (илл. 7.41, стр. 783–784): МСЭ vs IETF; монолитная vs модульная; двоичный vs ASCII; 1400 vs 250 страниц стандартов.

## 7.5 Доставка контента (стр. 785–807)

- Потоковое видео — >70 % интернет-трафика (стр. 785).

### Контент и интернет-трафик (стр. 786–788)

```
Закон Ципфа: доля заявок на k-й по популярности фильм ≈ C/k,
C = 1/(1 + 1/2 + ... + 1/N)
```
Немного популярных сайтов + длинный хвост непопулярных (стр. 786–788).

### Серверные фермы и веб-прокси (стр. 788–792)

- Ферма: кластер выглядит единым сайтом; балансировка через DNS (client mapping) или **IP anycast** (CloudFlare); front end, политика load balancing — циклическая или по заголовкам (илл. 7.43, стр. 788–790).
- Веб-прокси — общий кэш организации; выгода мала при >~100 пользователей; фильтрация контента, анонимность (илл. 7.44, стр. 791).

### Сети доставки контента (стр. 792–797)

> CDN, по сути, представляет собой огромный распределенный набор кэшей, которые доставляют контент клиентам напрямую (стр. 786).

- Akamai — первая крупная CDN (1998), применяет DNS; узел CDN — стойка внутри сети провайдера (стр. 792–793).
- **Переадресация DNS** двухуровневая: выбор близкой части сети + распределение нагрузки; ответы второго уровня с коротким TTL (стр. 793).
- HTTPS: узлу CDN нужны сертификат провайдера контента — CDN генерирует сертификат от его имени (стр. 794–795).
- Сопоставление клиентов опирается на EDNS Client Subnet; переход на DoH мешает, но CDN со своим DoH-распознавателем (CloudFlare, Google) выигрывают (илл. 7.46, стр. 795–796).

### Одноранговые сети (стр. 797–803)

- Napster (1999): 50 млн пользователей, централизованный каталог — единая точка отказа; закрыт судом (стр. 797–798).
- Gnutella (2000): полностью распределённый поиск «сплетнями»; проблемы: фрирайдинг (~70 %), масштабирование, загрязнение контента; ультрапиры (стр. 798–799).
- **BitTorrent** (2001): торрент-файл = трекер + список сегментов; сегменты 64–512 Кбайт, имя сегмента — 160-битный SHA-1; **трекер** (или DHT) ведёт список пиров — рой (swarm); **сидеры** имеют все сегменты; скачивание редких сегментов; стратегия «око за око» (tit-for-tat), личеры; целостность — сверка SHA-1 (илл. 7.47, стр. 799–802).

### Эволюция интернета (стр. 803–807)

- Вехи: 21.11.1969 (UCLA–SRI), 01.01.1983 (TCP/IP), 1989 (WWW) (стр. 803). Сейчас — облачные ЦОД и CDN (илл. 7.49, стр. 804–805).
- Akamai: >200 000 узлов, >120 стран; CloudFlare — >90 стран (стр. 805).
- Точки обмена: DE-CIX ~2000 сетей, AMS-IX и LINX ~по 1000; линии OC-192 (9,6 Гбит/с) и OC-768 (38,5 Гбит/с) (стр. 806).

## 7.6 Резюме (стр. 807–808)

- DNS — иерархическое именование через распределённую БД; шифрование DNS может централизовать службу и изменить архитектуру интернета (стр. 807).
- Почта: RFC 5321/5322 + MIME, доставка SMTP; веб — от статичных HTML к динамическому контенту и повсеместному отслеживанию (стр. 807).
- Потоковая передача сохранённых файлов — по TCP; реальное время — IP-телефония; популярные сайты — CDN, альтернатива — P2P (стр. 807–808).
