## Оглавление главы

3.1 Ключевые вопросы (242) · **3.2 Обнаружение и коррекция ошибок (252)** · 3.3 Элементарные протоколы (266) · **3.4 Повышение эффективности: раздвижное окно (277)** · 3.5 Практические протоколы: SONET/PPP, ADSL, DOCSIS (296)

Границы главы: LLC здесь **не рассматривается**; MAC упомянут один раз — «представлен в главе 4» (стр. 303). Фрейм Ethernet в главе тоже нет (только CRC-32 как носитель, стр. 265) — см. [[Заголовки протоколов]] и [[Глава 4]].

Определение уровня (стр. 242): надёжная и эффективная передача **фреймов** между двумя **смежными** устройствами по каналу, где биты приходят в порядке отправления. Фрейм = Header + Payload + Trailer (илл. 3.1). Заголовок фрейма не передаётся сетевому уровню ни при каких обстоятельствах (стр. 268–269) — полное разделение уровней.

## 3.1 Четыре задачи канального уровня (стр. 242–252)

1. Интерфейс для сетевого уровня; 2. фрейминг; 3. обработка ошибок; 4. управление потоком (стр. 242).

Службы сетевому уровню (стр. 243–244):

| Служба | Гарантия | Пример |
| --- | --- | --- |
| Без подтверждений, без соединения | ничего | Ethernet |
| С подтверждениями, без соединения | каждый фрейм подтверждён; дубликаты возможны | 802.11 |
| С подтверждениями, с соединением | каждый фрейм ровно один раз, по порядку | спутниковые каналы |

Подтверждения на канальном уровне — оптимизация: в надёжных каналах не нужны, в беспроводных окупаются (стр. 244–245).

Фрейминг — четыре метода (илл. 3.4, стр. 246–250):

1. **Подсчёт байтов** — ошибка в счётчике теряет синхронизацию навсегда; практически не применяется.
2. **Флаговые байты + байт-стаффинг** — `FLAG = 0x7E`, ESC = 0x7D; модель PPP.
3. **Сигнальные биты + бит-стаффинг** — флаг 01111110, после пяти единиц вставляется 0; фреймы произвольного размера; HDLC; накладные ≈ 12,5 %; применяется в USB.
4. **Запрещённые сигналы физического уровня** — в 4B/5B из 32 сигналов 16 не используются, часть — под границы фрейма.

Перед фреймом — **преамбула** (у 802.11 — 72 бита) для настройки приёмника (стр. 249–250). Требование к нумерации: доставка «ровно один раз» (стр. 250–251). Rate-based управление потоком — только транспортный уровень ([[Глава 6]]), здесь — с обратной связью (стр. 251).

## 3.2 Обнаружение и коррекция ошибок (стр. 252–266)

Две стратегии (стр. 253): **FEC** — получатель исправляет сам; **коды обнаружения** — повтор. Ограничение: избыточные биты тоже могут быть повреждены.

Модели ошибок (стр. 253–254): изолированные однобитовые (тепловой шум); пакеты ошибок (замирание); канал со стиранием (место ошибки известно — исправлять проще).

Понятия (стр. 255): (n, m)-код, кодовое слово, блочный/систематический/линейный код, кодовая норма m/n (1/2 — зашумлённый канал).

| Задача | Минимальное расстояние Хэмминга |
| --- | --- |
| Обнаружить d ошибок | ≥ d + 1 |
| Исправить d ошибок | ≥ 2d + 1 |

### Код Хэмминга (стр. 256–258)

Проверочные биты на позициях 1, 2, 4, 8, 16…; бит данных `k` проверяют те контрольные, чьи номера входят в разложение `k` по степеням двойки (11 = 8+2+1 ⇒ p1, p2, p8). Нижний предел (3.1): `m + r + 1 ≤ 2^r` — метод Хэмминга его достигает. Синдром ошибки указывает ошибочный бит. Код (11,7) имеет расстояние 3. Применение — ECC RAM.

### Другие коды (стр. 258–262)

| Код | Ключевое |
| --- | --- |
| **Сверточный** (NASA) | r = 1/2, k = 7; Voyager 1977; GSM, спутники, 802.11. Единственный неблочный; декодирование — Витерби |
| **Рида — Соломона** | работает с m-битовыми символами; слово 2^m − 1 символов (m=8 ⇒ 255 байт); 2t избыточных символов исправляют t ошибок; DSL, кабельные, спутники, CD/DVD/Blu-ray |
| **LDPC** | Галлагер 1962, переоткрыт 1995; итеративное декодирование; цифровое ТВ, 10 Гбит/с Ethernet, 802.11 |
| **Код чётности** | 1 бит, расстояние 2, обнаруживает одну ошибку |

Чередование (interleaving) (стр. 260–261): матрица n×k, чётность по строкам, порядок отправки ≠ порядок вычисления; превращает защиту от изолированных ошибок в защиту от пакетов. n бит чётности на блок k·n бит обнаруживают один пакет ≤ n.

Контрольная сумма (стр. 261–262): 16-битная сумма IP с дополнением до единицы; не ловит перестановки, добавление нулей, склейку пакетов; Флетчер (1982) — точнее.

### CRC (стр. 262–266)

Биты = коэффициенты многочлена; арифметика по модулю 2 (XOR). Стороны договариваются о `G(x)` (старший и младший биты = 1); передаваемый фрейм делится на `G(x)` без остатка; у получателя ненулевой остаток ⇒ ошибка.

```
T(x) = x^r·M(x) XOR остаток от деления x^r·M(x) на G(x)
Пример: фрейм 1101011111, G(x) = 10011 (x⁴+x+1) → T = 11010111110010
```

Ошибки `[T(x)+E(x)]/G(x) = E(x)/G(x)` ⇒ незамечены только ошибки, кратные `G(x)`.

| Тип ошибки | Условие обнаружения |
| --- | --- |
| Однобитовая | все, если G(x) ≥ 2 членов |
| Две изолированные | если xᵏ+1 не делится на G(x) (для x¹⁵+x¹⁴+1 — k до 32768) |
| Нечётное число битов | все, если G(x) делится на (x+1) |
| Пакет ≤ r бит | все, если G(x) содержит x⁰ |
| Пакет r+1 бит | пропуск (1/2)^(r−1) |
| Пакет > r+1 бит | пропуск (1/2)^r |

Стандарт IEEE 802 (Ethernet): `x³²+x²⁶+x²³+x²²+x¹⁶+x¹²+x¹¹+x¹⁰+x⁸+x⁷+x⁵+x⁴+x²+x+1` — ловит любые пакеты ≤ 32 бит (стр. 265). Реализация — регистр сдвига (Петерсон, Браун, 1961). **CRC не исправляет** и не абсолютно в обнаружении (стр. 266).

## 3.3 Элементарные протоколы (стр. 266–277)

Допущения (стр. 266–267): независимые процессы (физический уровень и часть канального — на NIC, остальное — драйвер); канал ненадёжен, теряет фреймы целиком; компьютеры не ломаются.

Фрейм (илл. 3.11): `kind, seq, ack` — заголовок; `info` — данные; `MAX_PKT = 1024`.

| Протокол | Что добавляет |
| --- | --- |
| **1 — «Утопия»** | ничего: ошибок нет, буферы бесконечны |
| **2 — stop-and-wait** | управление потоком: подтверждение перед следующим фреймом |
| **3 — PAR/ARQ** | нумерация (MAX_SEQ = 1, один бит достаточно) + таймер + повтор |

В протоколе 3: потерянное подтверждение ⇒ повтор ⇒ дубликат дошёл бы до сетевого уровня без нумерации (стр. 275). Один бит достаточен, потому что неопределённость только между соседними фреймами.

## 3.4 Дуплексные протоколы с раздвижным окном (стр. 277–296)

**Piggybacking** (стр. 278–279): подтверждение прикрепляется к встречному фрейму данных (поле ack); отдельный вспомогательный таймер, короче таймера отправителя.

Раздвижное окно (стр. 280–282): передающее окно — отправлены, не подтверждены; приёмное окно — что готов принять; вне окна — отбрасывается; размеры окон могут различаться. Поле номера n бит ⇒ номера 0…2ⁿ−1.

Спутниковый пример (стр. 282–284): 50 Кбит/с, фрейм 1000 бит, задержка 500 мс в обе стороны ⇒ stop-and-wait использует 4 % полосы.

```
BD = полоса × задержка (в одну сторону) ÷ размер фрейма   — во фреймах
w = 2·BD + 1
Пример: 50 Кбит/с × 250 мс = 12,5 фрейма ⇒ w = 26
```

**Возврат к n vs выборочный повтор** (стр. 284–286):

| | Возврат к n | Выборочный повтор |
| --- | --- | --- |
| Получатель | игнорирует всё после ошибочного | буферизует последующие |
| Окно получателя | 1 | > 1 |
| По тайм-ауту | повторяет все неподтверждённые | только самый старый |
| NAK | нет | да |

**Протокол 4** — однобитное окно, дуплексный; поле ack = номер последнего принятого фрейма (стр. 285–286). Преждевременный тайм-аут при одновременном старте ⇒ половина фреймов — дубликаты (илл. 3.17).

**Протокол 5 — возврат к n** (стр. 286–291): MAX_SEQ = 7. Потолок неподтверждённых = MAX_SEQ (не +1): при 8 отправитель не отличил бы «все дошли» от «все потеряны» (стр. 287). Кумулятивное подтверждение. Таймер — на каждый фрейм.

**Протокол 6 — выборочный повтор** (стр. 291–296): окно ≤ половины пространства номеров (`NR_BUFS = (MAX_SEQ+1)/2 = 4` при 3 битах) — иначе перекрытие окон путает новые фреймы со старыми (илл. 3.22). NAK: на повреждённый фрейм и на неожиданный номер; по одному NAK на фрейм (`no_nak`). Вспомогательный таймер ack_timer шлёт отдельное подтверждение, когда встречного трафика нет.

## 3.5 Практические протоколы (стр. 296–305)

Три случая линий «точка-точка»: SONET, ADSL, DOCSIS — везде PPP, но по-разному (стр. 296).

### PPP (стр. 296–300)

Три задачи: фрейминг, **LCP** (установление/согласование), **NCP** (свой на каждый протокол сетевого уровня).

| Поле PPP | Байты | Значение |
| --- | --- | --- |
| Flag | 1 | 0x7E |
| Address | 1 | 0xFF — «все станции» |
| Control | 1 | 0x03 — ненумерованный |
| Protocol | 1–2 | IP/IPX/AppleTalk или LCP/NCP |
| Payload | — | по умолчанию 1500 |
| Checksum | 2 (до 4) | — |

Стаффинг: `0x7E` в payload → `0x7D 0x5E` (XOR 0x20). PPP байт-ориентированный и обычно без подтверждений (ненумерованный режим); HDLC бит-ориентированный и надёжный. Состояния: DEAD → ESTABLISH → AUTHENTICATE → NETWORK (NCP, для IP — выдача адресов) → OPEN → TERMINATE (илл. 3.25). В SONET поверх PPP — скремблирование для частых смен битов (стр. 299).

### ADSL (стр. 300–303)

Стек: IP → PPP → Ethernet → AAL5 → ATM → ADSL (илл. 3.26). **ATM**: ячейки 53 байта = 48 + 5; с соединением; 48 — компромисс Европа(32)/США(64) (стр. 300–301). **AAL5**: Pad до кратности 48, Length (2) + CRC-32 (4); адреса в AAL5-фрейме не нужны, CRC PPP избыточен (стр. 301–302). Физический уровень ADSL: Рида — Соломона + 1-байтный CRC — линии зашумлённее SONET (стр. 302).

### DOCSIS (стр. 303–305)

PHY (PMD) + MAC ([[Глава 4]]). Входящий пакет 204 байта (184 полезных, MPEG-2-совместимость); DOCSIS 3.0 — связывание до 32 входящих/8 исходящих каналов 6–8 МГц; 3.1 — OFDM, 192/96 МГц. Порядок байтов сетевой (стр. 304–305). В переводе опечатка: «2027 байт, 1799 данных + 225 чётности» (1799+225 = 2024).
