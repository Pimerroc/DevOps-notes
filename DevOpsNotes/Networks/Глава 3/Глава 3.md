## ⚠️ Что важно знать о границах главы

Глава 3 в 6-м издании **обрывается на полпути**: разбиение канального уровня на **LLC** и **MAC** здесь **не рассматривается**. Слова LLC в главе 3 нет ни разу; MAC упомянут ровно один раз — «уровень управления доступом к среде (Media Access Control, MAC), **представленный в главе 4**» (стр. 303).

**Чего в главе 3 нет** (и не надо искать):
- LLC, LLC/SNAP, раздеение канального уровня на подуровни;
- структуры кадра Ethernet как таковой — Ethernet упомянут только как пример службы без подтверждений (стр. 244) и как носитель CRC-32 (стр. 265, 302);
- таблицы кодов в формате «мин. длина кадра / разряды / вероятность необнаруженной ошибки» — вместо неё даны правила обнаружения для полинома с `r` контрольными битами;
- VPI/VCI, STS/SDH, FСS, BER как термины, CRC-CCITT/CRC-16.

Всё это — материал [[Глава 4]] и [[Глава 2]].

> [!tip]- Где какой подуровень канального уровня
> Уровень разделён надвое по признаку **зависит ли функция от физической среды**:
>
> ```
> канальный уровень
> ├── LLC  ← НЕ зависит от среды: фрейминг, ошибки, поток     → ЭТА ГЛАВА
> │        и определение, какой протокол внутри (поле Type)
> └── MAC  ← ЗАВИСИТ от среды: кто говорит следующим         → [[Глава 4]]
> ```
>
> Почему граница проходит именно так, почему слово «под» появилось в названии главы 4, почему MAC адресует **интерфейс**, а не устройство, и почему ARP работает только для следующего хопа — в разделе «Что такое MAC на самом деле»
> в [[Глава 4]]. Читай его, если привычка «MAC = серийный номер» мешает различать две задачи: **кто говорит следующим** и **как зовут получателя**.

## О чём глава

3.1 Четыре задачи канального уровня · 3.2 **Обнаружение и коррекция ошибок** · 3.3 Симплексные протоколы (1–3) · 3.4 **Дуплексные протоколы с раздвижным окном** (4–6) · 3.5 Практические протоколы: SONET/PPP, ADSL, DOCSIS

**Определение уровня** (стр. 242): надёжная и эффективная передача целых блоков — **фреймов** — между двумя **смежными** устройствами по каналу, где биты принимаются в том же порядке, в каком передаются (принцип провода).

**Фрейм = Header + Payload + Trailer** (илл. 3.1). Заголовок фрейма сетевому уровню **никогда не передаётся** (стр. 268) — это обеспечивает полное разделение уровней: пока сетевой уровень ничего не знает о формате фрейма, изменение канального не требует замены его программного обеспечения.

## 3.1 Четыре задачи

1. Строго очерченный служебный интерфейс для сетевого уровня.
2. Формирование отдельных фреймов из потока байтов.
3. Обнаружение и исправление ошибок передачи.
4. Управление потоком — чтобы быстрый отправитель не «затопил» медленного получателя.

### Службы сетевому уровню

| Служба | Гарантирует | Пример из текста |
| --- | --- | --- |
| Без подтверждений и без соединения | Ничего | **Ethernet** (стр. 244) |
| С подтверждениями, без соединения | Каждый фрейм подтверждён; при отсутствии подтверждения — повтор. Дубликаты возможны | **802.11** (стр. 244) |
| С подтверждениями, с соединением | Все фреймы приняты, каждый ровно один раз, в правильном порядке | Спутниковый канал, междугороднее соединение |

> [!warning]- Почему подтверждения на канальном уровне — «скорее оптимизация, чем требование»
> Сетевой уровень всегда может ждать подтверждения сам, но это неэффективно: ему неизвестны максимальная длина фрейма и задержка доставки. Пример: сообщение делится на **10 фреймов**, в среднем **два** теряются — повтор всей передачи занимает очень много времени.
> В надёжных каналах (оптоволокно) накладные расходы на подтверждения только снижают пропускную способность; в беспроводных — окупаются.

Три фазы службы с соединением: **установление** → **передача** → **разрыв**.

### Формирование фрейма — четыре метода

![[ch3-framing.png]]

Подробности по каждому:

1. **Подсчёт байтов** — в поле заголовка число байт фрейма. **Практически не применяется:** ошибка в одном бите счётчика (`5 → 7`) теряет синхронизацию навсегда; даже если контрольная сумма не сойдётся, начало следующего фрейма определить нельзя, а повтор бессмысленен.
2. **Флаговые байты + байт-стаффинг** — `FLAG = 0x7E`, два соседних флага = граница; перед случайно совпавшим флагом вставляется `ESC = 0x7D`. Упрощённая модель **PPP**. Накладные: без флагов ≈ 100 байт, одни флаги ≈ **200 байт**.
3. **Сигнальные биты + бит-стаффинг** — флаг `01111110`; после **пяти единиц подряд** вставляется нулевой бит. Позволяет фреймы **произвольного размера в битах** (не кратного 8). Применён в **HDLC**. Накладные ≈ **12,5 %**. Гарантирует минимальную плотность передачи для синхронизации физического уровня — отсюда применение в **USB**.
4. **Запрещённые сигналы физического уровня** — эксплуатируются «нарушения правил кодирования»: в линии `4B/5B` из 32 возможных сигналов **16 не используются**, часть зарезервирована под границы фрейма.

> [!tip]- Общее для Ethernet и 802.11
> Фрейм начинается с **преамбулы** (preamble) — чётко заданного шаблона, по которому приёмник настраивает уровень и тактовую частоту ещё до прихода данных.
> У 802.11 преамбула — **72 бита**. Вслед за ней идёт поле длины (счётчик битов).

### Обработка ошибок и управление потоком

**Требование к нумерации фреймов** (стр. 250–251): доставка каждого фрейма «**ровно один раз, не больше и не меньше**» — иначе получатель не отличит повтор от оригинала.

> [!danger]- Проклятая четвёрка «PCS»
> **Управляющие фреймы с обратной связью** · **последовательная нумерация фреймов** · **таймеры канального уровня** · **управление потоком**. Это четыре неразрешимые проблемы, породившие протоколы 1–6.

- **Таймер**: после передачи включается на интервал, достаточный для приёма, обработки и возврата подтверждения. Истёк → повтор.
- **Управление потоком с обратной связью** — получатель разрешает продолжить передачу. Именно его разбирает глава.
- **Управление потоком с ограничением** (rate-based) — ограничение скорости без обратной связи. **Применяется исключительно на транспортном уровне** (глава 6), не здесь.
- **Аппаратная заметка**: канальный уровень обычно реализован в виде **NIC** и работает со скоростью передачи по кабелю.

> [!warning]- «Пожарный шланг»
> Метафора из книги: мощный отправитель заливает бедный смартфон. Даже при полном отсутствии ошибок получатель не успевает обрабатывать кадры. **Переполнение** при этом решается на более высоких уровнях, а не здесь.

## 3.2 Обнаружение и коррекция ошибок

![[ch3-error-codes.png]]

### Две стратегии

| Стратегия | Что добавляет | Что делает получатель |
| --- | --- | --- |
| **Корректирующие коды** (использование = **FEC**, Forward Error Correction, упреждающая коррекция) | Избыточность, по которой можно определить, какие данные **должны были прийти** | Сам **исправляет** |
| **Коды обнаружения ошибок** | Избыточность = **только оповещение**, без указания типа | Запрашивает **повтор** |

**Ограничение обеих стратегий:** биты надёжности сами могут быть повреждены — канал не различает служебные биты и биты данных.

### Три модели ошибок

1. **Изолированные однобитовые** — от теплового шума.
2. **Пакеты (последовательности) ошибок** — глубокое замирание беспроводного канала, временная электрическая помеха в кабеле. Числа: блок 1000 бит, вероятность 0,001 на бит. При независимых ошибках повреждён почти каждый блок; при пакетных — в среднем **один блок из ста**. Но **последовательность исправлять намного сложнее**.
3. **Канал со стиранием** (erasure channel) — местоположение ошибки известно (физический уровень сообщает «бит потерян»). Исправлять **проще**, но воспользоваться удаётся нечасто.

> [!tip]- Методическая рекомендация из книги
> Коды — прикладная математика. **Не конструируйте свои коды**, берите проверенные:
> Хэмминга, Рида — Соломона, LDPC.

### Корректирующие коды: понятия

Фрейм = `m` информационных битов + `r` избыточных; полная длина `n = m + r` → обозначение **(n, m)-код**.

- **Кодовое слово** — все `n` бит вместе.
- **Блочный код**: `r` — простая функция от `m`.
- **Систематический код**: `m` бит пересылается напрямую, не кодируется.
- **Линейный код**: `r` — линейная функция от `m` (обычно XOR).
- **Кодовая норма** = `m/n`. Для зашумлённого канала обычна **1/2**; в хороших — близка к 1.

**Расстояние Хэмминга** — число различающихся разрядов в двух кодовых словах. Пример: `10001001` XOR `10110001` = `00111000` → различаются **3 бита**.

| Задача | Минимальное кодовое расстояние |
| --- | --- |
| Гарантированно **обнаружить** `d` ошибок | ≥ `d + 1` |
| **Исправить** `d` ошибок | ≥ `2d + 1` |

**Пример кода из 4 слов:** `0000000000`, `0000011111`, `1111100000`, `1111111111`. Расстояние **5** → исправляет **двойные** ошибки и обнаруживает **четверные**.

> [!warning]- Ограничение, о котором забывают
> Исправлять двойные **и** одновременно обнаруживать четверные **невозможно**:
> одно и то же принятое слово пришлось бы интерпретировать двумя способами.

### Код Хэмминга

- Биты нумеруются **слева направо с 1**.
- **Проверочные биты** — на позициях **1, 2, 4, 8, 16, …** (степени двойки).
- **Биты данных** — остальные: 3, 5, 6, 7, 9, 10, …
- Номер бита данных `k` раскладывается на степени двойки; бит `k` проверяется только теми контрольными битами, номера которых входят в это разложение. **11 = 8 + 2 + 1** → бит 11 проверяют `p1`, `p2`, `p8`.

**Формула (3.1) — нижний предел контрольных бит:**

```
Каждому из 2^m сообщений соответствует n недопустимых слов на расстоянии 1
  ⇒ каждое сообщение требует n + 1 слов ⇒ (n + 1)·2^m ≤ 2^n;  n = m + r
  ⇒  m + r + 1 ≤ 2^r
```

Метод Хэмминга (Hamming, 1950) **достигает** этого предела.

**Синдром ошибки** — ненулевой набор результатов перепроверки; по нему определяется и исправляется ошибочный бит. Код (11, 7) имеет расстояние **3** → исправляет одиночные ошибки или обнаруживает двойные.

**Применение:** код Хэмминга используется в физических модулях **RAM**.

### Другие коды

| Код | Ключевое |
| --- | --- |
| **Сверточный код NASA** | `r = 1/2`, `k = 7`; впервые — Voyager (1977); ныне GSM, спутники, **802.11**. Шесть регистров, 7 сдвигов. Единственный код главы, **не блочный**: нет границы кода, нет ограничения на размер сообщения. Декодирование — алгоритм **Витерби** |
| **Рида — Соломона** | Работает с **m-битовыми символами**, не с битами. Длина кодового слова `2^m − 1` символов; при `m = 8` → **255 байт**. `2t` избыточных символов исправляют до `t` ошибок; при 32 избыточных — **16** символов, то есть пакеты **в 128 бит**. Декодирование — **Берлекэмп — Мэсси**. Применение: DSL, кабельные и спутниковые сети, CD, DVD, Blu-ray |
| **LDPC** | Low-Density Parity Check. Изобретён Галлагером в **1962**, заново — в **1995**. Каждый выходной бит из подмножества входных ⇒ матрица с низкой плотностью единиц. Декодирование — итеративное приближение. Цифровое ТВ, **Ethernet 10 Гбит/с**, ЛЭП, последние версии 802.11 |
| **Код чётности** | Один бит; расстояние **2** → обнаруживает **одну** однобитовую ошибку. `1011010` → `10110100` (чёт) или `10110101` (нечёт) |

> [!tip]- Мягкое и жёсткое принятие решений
> Пример: `–1 В` соответствует логическому 0, `+1 В` — логической 1; получены `0,9 В` и `–0,1 В`. Вместо жёсткого решения («1» и «0») можно трактовать `0,9 В` как «очень вероятную единицу» — это **soft-decision decoding**. Решение «0 или 1»
> до исправления = **hard-decision decoding**.

### Чередование (interleaving)

**Проблема:** один бит чётности на блок гарантирует обнаружение только одной однобитовой ошибки; при длинной последовательности вероятность обнаружения — всего **0,5**.

**Схема:** блок представить матрицей `n` бит шириной × `k` бит высотой, вычислить **один бит чётности для каждой строки**. **Чередование**: биты чётности вычисляются **в порядке, отличном от порядка отправки данных**.

**Свойства:**
- Чередование превращает код, работающий с **изолированными** ошибками, в код, работающий с **пакетами** ошибок.
- Пакет длиной `n` разбрасывается по **разным столбцам** ⇒ в каждом не более одного бита ⇒ биты чётности его выявят.
- **Общее правило:** `n` бит чётности на блок из `k·n` бит обнаруживают **одну** последовательность длиной **≤ n**. Последовательность длиной `n + 1` не будет обнаружена, если инвертированы **только первый и последний** биты.

> [!warning]- Существенная оговорка из текста
> «Последовательность ошибок» **не предполагает**, что все биты в ней неправильные — ошибки есть **как минимум в первом и последнем** битах. На илл. 3.8 из семи «сбойных» битов изменено только четыре.

### Контрольная сумма

Под «контрольной суммой» понимают **любую группу контрольных битов**, связанных с сообщением. Помещается в конец сообщения. Обнаружение: просуммировать всё полученное кодовое слово; **результат 0 ⇒ ошибок нет**.

**16-битная контрольная сумма IP** (Braden et al., 1988): сумма битов сообщения, разбитого на **16-битные слова**. Работает со словами, а не с битами ⇒ ошибки, сохраняющие чётность, всё же меняют сумму. Используется **дополнение до единицы** (на компьютерах — **дополнение до двух**), а не сумма по модулю 2¹⁶, причём переполнение старших битов возвращается к младшим. У дополнения до единицы **два представления нуля**.

> [!note]- Критика (Partridge et al., 1995)
> Десятилетиями считалось, что биты с контрольной суммой случайны; анализ реальных данных показал, что предположение **неверно** ⇒ нераспознанные ошибки проскакивают заметно чаще.
> Простая сумма не распознаёт удаление или добавление нулевых данных, перестановки частей сообщения, «склейку» частей двух разных пакетов. **Контрольная сумма Флетчера** (1982)
> добавляет произведение данных и их позиции — точнее ловит изменения положения.

### CRC — циклический избыточный код

**Биты как многочлены.** Фрейм из `k` бит — список коэффициентов многочлена степени `k − 1`. Пример: `110001` → `x⁵ + x⁴ + x⁰`. Арифметика **по модулю 2**: переноса при сложении нет, заёма при вычитании нет; сложение и вычитание **эквивалентны XOR**.

**Идея.** Стороны договариваются об образующем многочлене `G(x)`; старший и младший биты в нём равны 1. Добавить CRC так, чтобы полученный многочлен **делился на `G(x)` без остатка**. Получатель делит принятое на `G(x)`; **ненулевой остаток ⇒ ошибка**.

**Алгоритм:**

```
1. r = степень G(x). Дописать r нулей в конец фрейма → многочлен x^r·M(x)
2. Разделить по модулю 2 битовую строку x^r·M(x) на строку G(x)
3. Вычесть по модулю 2 остаток (не более r бит) → передаваемый фрейм T(x)
```

**Пример из илл. 3.9:**

```
фрейм:      1101011111           (10 бит)
G(x) =      10011               = x⁴ + x + 1
+ 4 нуля:   1101011111 0000      (14 бит)
остаток:    0010
T(x) =      11010111110010      (14 бит) — делится на G(x) без остатка
```

> [!tip]- Почему это работает
> Приниматель вычисляет `[T(x) + E(x)] / G(x)`. Так как `T(x)/G(x) = 0`, результат равен **`E(x)/G(x)`**. Значит: ошибки, случайно оказавшиеся кратными `G(x)`, останутся незамеченными; остальные будут обнаружены.

**Что именно CRC обнаруживает** — самая полезная таблица главы:

| Тип ошибки | Условие | Результат |
| --- | --- | --- |
| **Однобитовая** | `E(x) = xⁱ`. Если `G(x)` содержит **два и более члена**, `E(x)` никогда не делится на `G(x)` | **Все** обнаруживаются |
| **Две изолированные** | `E(x) = xⁱ + xʲ = xʲ(x^{i−j} + 1)`. Достаточно, чтобы `xᵏ + 1` не делилось на `G(x)` | Пример: `x¹⁵ + x¹⁴ + 1` не делит `xᵏ + 1` ни для какого `k` = 1…**32768** |
| **Нечётное число битов** | Если `G(x)` **делящийся на `x + 1`** | Все нечётные обнаруживаются — по статистике уже **половина** ошибок |
| **Пакет длиной ≤ r** | Если `G(x)` содержит член `x⁰` | **Все** обнаруживаются |
| **Пакет длиной r + 1** | Остаток нулевой, только если пакет совпадает с `G(x)` | Вероятность пропуска **`(1/2)^(r−1)`** |
| **Длиннее r + 1** или несколько коротких | — | Вероятность пропуска **`(1/2)^r`** |

**Стандартный полином IEEE 802** (на нём построен Ethernet):

```
x³² + x²⁶ + x²³ + x²² + x¹⁶ + x¹² + x¹¹ + x¹⁰ + x⁸ + x⁷ + x⁵ + x⁴ + x² + x + 1
```

Обнаруживает **любые пакеты ошибок длиной не более 32 бит** и **все пакеты с нечётным числом битов**. Применяется с начала 1980-х.

> [!note]- CRC-32 — не лучший
> Расстояние Хэмминга для сообщений обычной длины у самых эффективных кодов CRC равно **6**, тогда как у стандартного CRC-32 (IEEE) — только **4** (Castagnoli et al., 1993; Koopman, 2002).

**Реализация:** Петерсон и Браун (1961) показали, что CRC — простая схема на базе регистра сдвига. Применяется **повсеместно в аппаратном обеспечении**: почти все LAN (Ethernet, 802.11) и линии «точка-точка».

> [!danger]- Ключевое, что надо запомнить про CRC
> **CRC не исправляет ничего.** Механизма выбора ближайшего кодового слова, как у Хэмминга с синдромом, здесь нет. И даже обнаружение **не абсолютно**: у него есть «слепые зоны», перечисленные выше.

## 3.3 Симплексные протоколы

![[ch3-protocols.png]]

### Допущения (разд. 3.3.1)

1. **Независимые процессы** — физический, канальный и сетевой уровни как отдельные процессы (илл. 3.10). Физический уровень и часть канального выполняются на **NIC**; остальное — на ЦП, часто в виде **драйвера устройства**.
2. **Однонаправленная передача данных** — A хочет передать B большой поток; надёжная служба с установлением соединения; у A **бесконечный источник** данных; компьютеры **не выходят из строя**.
3. Канал **ненадёжен** — случайно теряет целый фрейм.

### Структура фрейма (илл. 3.11)

```c
#define MAX_PKT 1024              /* пакет всегда MAX_PKT байт */
#define MAX_SEQ                    /* номера от 0 до MAX_SEQ */
typedef struct { frame_kind kind; seq_nr seq; seq_nr ack; packet info; } frame;
```

Первые три поля — **заголовок**; `info` — данные (в управляющем фрейме не используется). `#define inc(k)` — циклическое увеличение, макрос ради быстродействия.

### Протокол 1 — «Утопия»

Допущения: односторонняя передача; ошибок нет; сетевые уровни всегда готовы; буфер неограничен; линия **никогда** не теряет и не искажает фреймы. Ни нумерации, ни подтверждений ⇒ `MAX_SEQ` не требуется. Единственное событие: `frame_arrival`. Используется **только поле `info`**.

### Протокол 2 — симплексный с остановкой и ожиданием

Появляется **управление потоком**; ошибок по-прежнему нет.

**Отброшенные решения:** усилить приёмник; снизить скорость; неограниченный буфер. Всё это требует спецоборудования, ресурсы тратятся впустую при малой загрузке, а проблема лишь перекладывается на сетевой уровень.

**Принятое решение — обратная связь:** получив пакет, получатель шлёт маленькое служебное сообщение, разрешающее отправку следующего фрейма. Протоколы «послал один фрейм → ждёт подтверждения» называются **stop-and-wait**.

> [!warning]- Тонкость, которую легко пропустить
> Хотя **данные** идут симплексно, **фреймы** идут **и в обратную сторону** — значит, линия между канальными уровнями должна быть **двунаправленной**. Но протокол диктует **жёсткое чередование** направлений, поэтому хватило бы **полудуплексного** канала.
> «Симплексный» здесь — про **логику обмена данными**, а не про провод.

### Протокол 3 — PAR / ARQ

- **PAR** = Positive Acknowledgement with Retransmission
- **ARQ** = Automatic Repeat reQuest

Допущение добавлено: канал **ненадёжен**. `#define MAX_SEQ 1` — **достаточно одного бита**. Переменные: отправитель — `next_frame_to_send`; получатель — `frame_expected`.

**Почему одного бита достаточно:** неопределённость возможна только **между двумя соседними фреймами** `m` и `m+1` — событие, запускающее передачу `m+1`, это подтверждение `m`, а значит `m−1` уже подтверждён. Отсюда инвертирование по модулю 2.

**Сценарий, вскрывающий необходимость нумерации** (стр. 275): пакет 1 доставлен; **фрейм подтверждения полностью потерян**; таймер истёк; A пересылает фрейм; **дубликат** целиком доходит до B и передаётся сетевому уровню ⇒ файл на B будет неверным, ошибка не обнаруживается.

## 3.4 Дуплексные протоколы с раздвижным окном

### Вложенное подтверждение (piggybacking)

Наивное решение — два экземпляра симплексного протокола с раздельными каналами; пропускная способность обратного канала почти не используется.

Эффективнее — **один канал**: данные и подтверждения перемешиваются, различаются по полю `kind`. Получив фрейм данных, получатель **не шлёт подтверждение сразу**, а прикрепляет его через поле `ack` к исходящему фрейму. Поле `ack` — **всего несколько бит**; отдельный фрейм потребовал бы заголовка и контрольной суммы.

**Проблема:** как долго ждать? Дольше таймера отправителя — значит отправитель повторит фрейм. Решение: **ещё один интервал ожидания, меньший, чем у отправителя**.

### Раздвижное окно

| Понятие | Определение |
| --- | --- |
| **Поле номера** | `n` бит ⇒ максимум `2ⁿ − 1` |
| **Передающее окно** | Номера фреймов, которые разрешено передавать: уже отправленные, но не подтверждённые |
| **Приёмное окно** | Номера, которые получатель может принять. Попавший — буферизуется; с номером нижнего края — отдаётся наверх и окно сдвигается; не попавший — **удаляется** |
| **Соотношение окон** | Окна получателя и отправителя **не обязаны** совпадать по размеру |
| **Инвариант** | Физический канал доставляет фреймы **в порядке отправления**; сетевому уровню пакеты всегда в **строгом** порядке |

### Зачем большое окно — спутниковый пример

Протокол 4 на 50-килобитном спутниковом канале, фреймы по 1000 бит, прохождение в обе стороны 500 мс:

| Событие | Время |
| --- | --- |
| Начало отправки первого фрейма | `t = 0` |
| Фрейм полностью отправлен | `t = 20 мс` |
| Получатель принял целиком и выслал подтверждение | `t = 270 мс` |
| Отправитель получил подтверждение (лучший случай) | `t = 520 мс` |

Отправитель заблокирован `500/520 = 96 %` времени ⇒ использовано только **4 %** полосы.

```
BD = полоса (бит/с) × задержка в одну сторону ÷ бит во фрейме
   → BD измеряется числом фреймов

2BD  = фреймов в пути (неподтверждённых), если отправитель работает непрерывно
+1   = потому что подтверждение уходит только после полного фрейма данных

       w = 2·BD + 1
```

**Пример:** `50 Кбит/с × 250 мс = 12,5 Кбит = 12,5 фрейма` ⇒ `2BD + 1 = **26 фреймов**`.

Отправка нескольких фреймов подряд называется **конвейерной обработкой** (pipelining).

> [!note]- Границы формулы
> `w = 2BD + 1` — **верхняя граница**: не учитывает время обработки кадра и принимает длину фрейма подтверждения равной нулю. Другие ориентиры: канал **1 Гбит/с** с задержкой **1 мс** удерживает 1 Мбит; при `w = 1` даже задержка в один фрейм роняет эффективность **ниже 50 %**.

### Возврат к n против выборочного повтора

|  | **Возврат к n** (go-back-n) | **Выборочный повтор** (selective repeat) |
| --- | --- | --- |
| Получатель | **Игнорирует всё после ошибочного**, не подтверждает | **Буферизует** последующие; ошибочный отбрасывает |
| Окно получателя | **Размер 1** | **> 1** (нужна память) |
| По тайм-ауту | Пересылает **все** неподтверждённые, начиная с ошибочного | Пересылает **только самый старый** |
| **NAK** | Не используется | Часто комбинируется с **отрицательным подтверждением** |
| Недостаток | При высоком уровне ошибок теряется большая доля полосы | Требует много памяти |

### Протокол 4 — однобитное раздвижное окно

`#define MAX_SEQ 1`. **Дуплексный.** Поле подтверждения содержит номер **последнего** принятого без ошибок фрейма.

**Устойчивость:** никакая комбинация потерянных фреймов или преждевременных тайм-аутов не может заставить протокол выдать дубликат, пропустить пакет или зависнуть (илл. 3.17).

> [!warning]- Нештатная ситуация (илл. 3.17б)
> Обе стороны начали одновременно — **половина фреймов содержит дубликаты, несмотря на отсутствие ошибок в канале**. Причина — преждевременный тайм-аут. Если время ожидания истечёт слишком быстро, фрейм может быть послан **три и более раз**.

### Протокол 5 — возврат к n

```c
#define MAX_SEQ 7                       /* 2^n - 1 */
#define NR_BUFS ((MAX_SEQ+1)/2)
```

**Отказ от допущения** «у сетевого уровня всегда неограниченное количество пакетов»: появляется событие `network_layer_ready` и функции `enable_network_layer` / `disable_network_layer`.

> [!danger]- Почему неподтверждённых фреймов не MAX_SEQ + 1
> Сценарий (стр. 287): если бы неподтверждённых было **8**, отправитель отправил бы `0…7`, получил бы подтверждение 7, отправил бы снова `0…7`, получил бы **ещё одно** подтверждение 7 — и **не смог бы отличить**, что 8 новых фреймов дошли или что все 8 потеряны. Получатель в обоих случаях подтверждает 7. ⇒ потолок = **MAX_SEQ**, а порядковых номеров = MAX_SEQ + 1.

**Кумулятивное подтверждение:** подтверждение фрейма `n` автоматически подтверждает `n − 1, n − 2` и все предыдущие.

**Функция `between(a, b, c)`** возвращает `true`, если `a ≤ b < c` циклически.

Обработка `cksum_err`: **просто игнорируется**. Обработка `timeout`: `next_frame_to_send = ack_expected`, затем пересылаются **все** неподтверждённые.

**Таймеры:** на каждый неподтверждённый фрейм нужен **свой таймер**, считающийся независимо. Все таймеры симулируются **единственными аппаратными часами**; данные хранятся **связанным списком** (число тиков + номер фрейма + указатель).

### Протокол 6 — выборочный повтор

Пять событий (добавилось `ack_timeout`). Переменные: `no_nak = true`, `oldest_frame = MAX_SEQ + 1`.

> [!danger]- Проблема перекрытия окон (илл. 3.22) — ключевой момент главы
> 1. Все семь фреймов `0…6` доставлены; окно сдвинулось на `7, 0, 1, 2, 3, 4, 5`.
> 2. **Молния стирает все подтверждения.** Отправитель повторяет фрейм `0` — а он
>    **попадает в новое окно** и принимается как новый.
> 3. Фрейм `7` отдан наверх; проверка наличия фрейма `0` находит его и **отдаёт старый
>    буферизованный пакет как новый** ⇒ протокол не справился.
> 4. **Причина:** новое окно **перекрыло** старое, и получатель не может отличить
>    новые фреймы от повторно высланных старых.
> 5. **Решение:** сдвинутое окно не должно перекрывать исходное ⇒ размер окна **не должен
>    превышать половины** количества порядковых номеров.

Отсюда: `#define NR_BUFS ((MAX_SEQ+1)/2)` = **4** при 3-битных номерах.

**Число буферов** = размер окна, а не диапазон номеров: фрейм `i` кладётся в буфер `i mod 4`; `i` и `i + 4` «соревнуются» за буфер, но **никогда не оказываются в одном окне одновременно** (это означало бы окно размера ≥ 5). **Таймеров тоже 4**, по одному на буфер.

**Вложенное подтверждение больше не обязательно.** Протокол 5 предполагал довольно высокую загрузку обратного канала. В пределе (много данных в одну сторону, ничего в другую) протокол 5 **останавливается**, как только окно отправителя заполнится. В протоколе 6 есть **вспомогательный таймер** `ack_timer`; по его истечении отправляется **отдельное** подтверждение. Прерывание = событие **`ack_timeout`**. Требуется **всего один** такой таймер.

> [!warning]- Период вспомогательного таймера
> Должен быть **существенно короче** интервала ожидания подтверждения, иначе отправитель повторит передачу раньше, чем подтверждение дойдёт.

**NAK — когда и зачем:**

- Отправляется в двух случаях: фрейм пришёл **повреждённым** или его **номер отличается от ожидаемого**.
- Чтобы не слать несколько запросов на один фрейм, получатель помнит: `no_nak = true`, если для `frame_expected` NAK ещё не посылался.
- Если NAK повреждён или потерян — ничего страшного: у отправителя рано или поздно истечёт время ожидания ACK.
- Когда время прохождения **стабильно**, NAK **бесполезен** — таймер можно ставить «свободно». Когда сильно варьирует — NAK **существенно ускоряют** повторную передачу.

## 3.5 Практические протоколы

Большинство глобальных сетей построено на линиях «точка-точка». Три случая: **SONET** (оптоволокно между маршрутизаторами), **ADSL** (абонентский шлейф), **DOCSIS** (кабельный шлейф). Во всех трёх для пересылки пакетов используется **PPP**, но применяется по-разному.

### PPP

Улучшенный вариант **SLIP** (Serial Line Internet Protocol). Обнаруживает ошибки, поддерживает несколько протоколов, разрешает аутентификацию.

**Три назначения PPP:**

1. Метод формирования фреймов, однозначно обозначающий конец одного и начало следующего.
2. **LCP** (Link Control Protocol) — установление, тестирование, согласование параметров.
3. **NCP** (Network Control Protocol) — согласование параметров сетевого уровня; для каждого поддерживаемого протокола **свой NCP**.

**Формат фрейма PPP** в ненумерованном режиме (илл. 3.24):

| Поле | Байты | Значение |
| --- | --- | --- |
| Flag | 1 | `01111110` = **0x7E** |
| Address | 1 | `11111111` — «все станции должны принимать» |
| Control | 1 | `00000011` — ненумерованный фрейм |
| Protocol | 2 или 4 | С **бита 0** — IP v4, IP v6, IPX, AppleTalk; **с бита 1** — LCP и NCP |
| Payload | переменная | По умолчанию **1500 байт** |
| Checksum | 1 / 2 / 4 | Обычно **2 байта**, до **4** по договорённости |
| Flag | 1 | `01111110` |

**Стаффинг:** если `0x7E` встречается в Payload, перед ним ставится `0x7D`, а следующий байт складывается по модулю 2 с `0x20`. **`0x7D 0x5E`** — управляющая последовательность для `0x7E`.

> [!danger]- PPP против HDLC — не одно и то же
> Формат фрейма PPP **близок** к HDLC, но:
> - **PPP — байт-ориентированный** (байт-стаффинг, все фреймы — целое число байтов);
> - **HDLC — бит-ориентированный** (бит-стаффинг), что позволяет фрейм размером например **30,25 байта**.
>
> **HDLC обеспечивает надёжную передачу** раздвижным окном. PPP тоже может (RFC 1663), **но на практике применяется редко**: используется **ненумерованный режим** — служба без установления соединения и без подтверждений.

**Диаграмма состояний PPP** (илл. 3.25):

```
DEAD → ESTABLISH → AUTHENTICATE → NETWORK → OPEN → TERMINATE → DEAD
```

`NETWORK` — обмен пакетами NCP; для IP главная задача — **назначение IP-адресов** обеим сторонам.

**Скремблирование:** полезная информация складывается по модулю 2 с длинной **псевдослучайной последовательностью**. Нужно, потому что SONET для синхронизации требует частой смены значений битов — иначе длинная последовательность нулей от пользователя вызовет проблемы.

### ADSL

Стек протоколов (илл. 3.26):

```
Компьютер → IP → PPP → Ethernet        (помещение пользователя)
Модем DSL → AAL5 → ATM → ADSL → AAL5   (абонентский шлейф)
DSLAM (с маршрутизатором) → ATM → IP → PPP   (офис провайдера)
```

**ATM** (Asynchronous Transfer Mode) — канальный уровень, пересылает **ячейки** длиной **53 байта = 48 + 5**. Разработан в начале 1990-х; ожидания не оправдал (те же проблемы, что у OSI), но успех превзошёл: применяется в DSL и WAN-каналах телефонных сетей.

| Свойство ATM | Значение |
| --- | --- |
| «Асинхронная» | Не нужно отправлять ячейки постоянно, как биты в синхронных линиях |
| Ориентация | **С установлением соединения** |
| Длина ячейки | 53 байта |
| Почему маленькая | Гибкое разделение полосы; при передаче фрагментов голоса нет длинных задержек |
| Почему 48 | Компромисс между **32-байтными** ячейками (хотела Европа) и **64-байтными** (США). Не степень двойки — отражает **политическую** составляющую |

**AAL5** (ATM Adaptation Layer 5) — основной уровень адаптации для пакетных данных. Трейлер: **Length (2 байта) + CRC (4 байта)**; `Pad` от 0 до 47 байт дополняет фрейм до кратности **48 байтам**.

> [!tip]- Что здесь лишнее
> **Адреса внутри фрейма AAL5 не нужны** — идентификатор виртуального контура в каждой ячейке не даст ей заблудиться. **Код CRC протокола PPP не нужен**, поскольку AAL5 включает такой же CRC. **Механизмы формирования фрейма PPP не требуются** — работу выполняют ATM и AAL5.

**Физический уровень ADSL:** **Рида — Соломона** (FEC) + **1-байтный CRC**. Куда более сложный механизм, чем в SONET — линии ADSL **гораздо зашумленнее**.

### DOCSIS

**DOCSIS** = два компонента: **PHY** (физический уровень, иногда его называют **PMD** — Physical Media Dependent) и **MAC** (представлен в главе 4).

| Свойство | Значение |
| --- | --- |
| Входящий пакет | **204 байта**, из них **184** — пользовательские (код Рида — Соломона + служебные) |
| Значения выбраны | Для совместимости с цифровым ТВ (**MPEG-2**) |
| **DOCSIS 3.0** | Связывание до **32 входящих** и до **8 исходящих** каналов по 6–8 МГц |
| **DOCSIS 3.1** | OFDM; входящий до **192 МГц**, исходящий до **96 МГц**; можно связывать каналы **разных типов** |
| Порядок байтов | Младший бит передаётся первым; при многобайтовых значениях старшие байты **перед** младшими — **сетевой порядок** |

## Пары, которые путают чаще всего

| Пара | Разница |
| --- | --- |
| **Код обнаружения (CRC)** ↔ **код коррекции (Хэмминг)** | CRC только сообщает «испорчено, переспроси». Хэмминг по синдрому **точно указывает** ошибочный бит и восстанавливает его |
| **Ошибочный бит** ↔ **пакет ошибок** | Первое — от теплового шума, второе — от замирания и помех. Исправлять пакет **намного** сложнее |
| **Симплексный протокол** ↔ **симплексная линия** | Разные вещи: в протоколах 2–3 фреймы идут в обе стороны, линия **двунаправленная** |
| **Поле номера** ↔ **окно** | Поле = `n` бит ⇒ максимум `2ⁿ − 1`. Окно = **количество** одновременно неподтверждённых фреймов |
| **ACK** = «последний принятый» | А **не** «следующий ожидаемый». В коде: `s.ack = (frame_expected + MAX_SEQ) % (MAX_SEQ + 1)` |
| **Возврат к n** ↔ **выборочный повтор** | Первый: получатель **отбрасывает**, отправитель повторяет **всё**. Второй: получатель **буферизует**, повторяется только нужное |
| **PPP** ↔ **HDLC** | PPP байт-ориентированный и обычно без подтверждений; HDLC бит-ориентированный и надёжный |
| **ATM** ↔ **AAL5** | ATM — транспорт с ячейками по 53 байта; AAL5 — слой адаптации, где живёт IP |
| **LLC** ↔ **MAC** | MAC — доступ к среде (глава 4). LLC — логическая связь **над** MAC. **В главе 3 их нет** |

## Внутренние противоречия перевода — не ошибка студента

| Место | Что написано | Что с этим делать |
| --- | --- | --- |
| **Рида — Соломона** (стр. 258–259) | «(255, 233) добавляет **22** символа» и тут же «с **32** избыточными символами исправляет **16**» ошибок | Не строй расчёты на этой паре. Верное правило: `2t` избыточных ⇒ `t` ошибок |
| **DOCSIS** (стр. 304) | «кодовое слово до **2027** байт, где **1799** — данные и **225** — чётность» (`1799 + 225 = 2024`) | То же — не считай по этим числам |
| **Арифметика CRC** (стр. 254) | «допустимы `2ᵐ/2ⁿ` или `1/2ʳ` кодовых слов» | Запись некорректна; содержательно имеется в виду `2ⁿ/2ʳ = 2ᵐ` |
| **Размеры на илл. 3.28** | Колонка размеров на очистке не читается | Поля знакомы (V, Resv, PDU Ptr, Start/End of Next PDU), размеры — нет |
| **E1** (стр. 181, глава 2) | «2048 Мбит/с» | Опечатка: должно быть 2,048 Мбит/с |
