# Лаба: DNS, TLS и сокеты — `dig`, `curl`, `openssl`, `ss`

> [!info] Цель
> Собрать доказательства по практике P1–P5 квиза 7–8: увидеть делегирование DNS своими глазами, проверить DNSSEC валидатором, разобрать TLS-хендшейк и цепочку сертификатов, прочитать состояния сокетов.
> Вопросы квиза — [[Квиз 7–8|Квиз 7–8]].

> [!note] Добавлено агентом
> Скелет лабораторной: команды, чек-листы наблюдений и критерии. Выводы и raw-вывод заполняет пользователь.

**Окружение:** Arch Linux; `dig` 9.20.30; `curl` 8.23.0 (HTTP2, HTTP3); `OpenSSL` 4.1.0; `iproute2` 7.3.0. Все команды read-only: только запросы и чтение состояния, изменений в системе нет.

**Бюджет времени:** ~60–70 мин (10–15 мин на пункт).

**Правило записи:** на каждый пункт — команда, 5–10 строк вывода, 3–6 предложений разбора, источник. Без вывода ответ не принимается.

При попытке получить ip некоторого DNS`а, он запрашивает у рекурентного распознавателя, тот выполняет итеративный поиск (в нашем случае этим занимается dig), для нашего случая запрос на edu.vsu.ru. Он первым делом он опросил ip нескольких корневых серверов в своем списке, один из них (e.root-servers.net) выдал адрес сервера доменна ответственного за .ru и так далее пока не достиг конечного искомого домена. В случае же dnssec наши возвращенные запросы подписаны anchore доверенным доменном, а также с сигнатурой RRSIG, которая представляет собой подпись RRset закрытым zsk (zone signing key), также присутствует dnskey rrset подписанный ksk (key signing key) (пара закрытых и открытых ключей, которые подписывают DNSKEY, RRSET, ссылка на открытый ключ ksk как раз и есть DS (delegation signer) - это хеш публичного ключа предоставленного родителем).
`aa` (Athoritive Answer)- это показатель того, что запись конечная (тоесть это авторитетный сервер для данного домена)
[stackoverflow](https://serverfault.com/questions/729025/what-are-all-the-flags-in-a-dig-response)
```text
I am using [RFC 1035](http://www.ietf.org/rfc/rfc1035.txt) as source, keeping to the sequence from there, regardless if you already mentioned it in your question.

- QR specifies whether this message is a query (0), or a response (1)
- OPCODE A four bit field, only valid values: 0,1,2
- AA Authoritative Answer
- TC TrunCation (truncated due to length greater than that permitted on the transmission channel)
- RD Recursion Desired
- RA Recursion Available
- Z Reserved for future use. Must be zero

There were two more DNSSEC-related flags introduced in [RFC 4035](https://www.ietf.org/rfc/rfc4035.txt):

- CD (Checking Disabled): indicates a security-aware resolver should disable signature validation (that is, not check DNSSEC records)
- AD (Authentic Data): indicates the resolver believes the responses to be authentic - that is, validated by DNSSEC
```
