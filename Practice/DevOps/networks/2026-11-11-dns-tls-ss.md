# Лаба: DNS, TLS и сокеты — `dig`, `curl`, `openssl`, `ss`

> [!info] Цель
> Собрать доказательства по практике P1–P5 квиза 7–8: увидеть делегирование DNS своими глазами, проверить DNSSEC валидатором, разобрать TLS-хендшейк и цепочку сертификатов, прочитать состояния сокетов.
> Вопросы квиза — [[Квиз 7–8|Квиз 7–8]].

> Скелет лабораторной: команды, чек-листы наблюдений и критерии. Выводы и raw-вывод заполняет пользователь.

**Бюджет времени:** ~60–70 мин (10–15 мин на пункт).

**Правило записи:** на каждый пункт — команда, 5–10 строк вывода, 3–6 предложений разбора, источник. Без вывода ответ не принимается.

## P2. `dig +dnssec`: кто валидирует

```bash
dig +dnssec cloudflare.com
dig +dnssec @1.1.1.1 cloudflare.com
dig +dnssec @1.1.1.1 cloudflare.com DNSKEY
dig +dnssec @1.1.1.1 DS cloudflare.com
dig +dnssec @1.1.1.1 dnssec-failed.org
dig +dnssec +cd @1.1.1.1 dnssec-failed.org
```

**Что зафиксировать:**

- [ ] OPT PSEUDOSECTION: выставлен ли `flags: do` в ответе локального resolver'а и в ответе `1.1.1.1`.
- [ ] Флаги заголовка: есть ли `ad`; у кого.
- [ ] `RRSIG`: поле type covered, algorithm, key tag, inception/expiration.
- [ ] `DNSKEY`: flags `256` (ZSK) vs `257` (KSK), algorithm, key tag.
- [ ] `DS`: digest type, key tag — совпадает ли с key tag KSK.
- [ ] `dnssec-failed.org`: `SERVFAIL` против `NOERROR` с `+cd`; что это доказывает про валидацию.

## P3. `curl -vI`: HTTP и TLS в одном выводе

```bash
curl -vI https://example.com
curl -vI --http1.1 https://example.com
curl -sI https://example.com
curl --http3 -I https://cloudflare.com   # если UDP/443 не блокируется
```

**Что зафиксировать:**

- [ ] Строки `*`: ALPN, версия TLS, шифр, subject/issuer сертификата, дата истечения.
- [ ] Строка запроса `>`: метод, путь, версия, заголовки `Host`/`User-Agent`/`Accept`.
- [ ] Строка ответа `<`: `HTTP/2 200` или `HTTP/1.1 200` — что означает первая строка.
- [ ] Заголовки: `server`, `content-type`, `content-length`, `cache-control`, `strict-transport-security`, `alt-svc`.
- [ ] Разница `-I` и `GET`: тело не передаётся, но заголовки те же; что будет при `405`.
- [ ] Что изменилось с `--http1.1`: соединение, ALPN, заголовки.
- [ ] Есть ли `alt-svc` с `h3` и что это обещает.

**Артефакт:** статусная строка + строка TLS + 3 заголовка.

**Вывод (3–6 предложений):**

**Источник:** `man curl`; RFC 9110; RFC 9113; книга, 7.3.

## P4. `openssl s_client` + `x509`: цепочка и поля

```bash
openssl s_client -connect example.com:443 -servername example.com -showcerts </dev/null
openssl s_client -connect example.com:443 -servername example.com </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates -ext subjectAltName
openssl s_client -brief -connect example.com:443 -servername example.com </dev/null
```

**Что зафиксировать:**

- [ ] `Verify return code` — `0 (ok)` или ошибка; что именно проверялось.
- [ ] Цепочка: leaf → intermediate → root; сколько сертификатов в `-showcerts`.
- [ ] `subject`/`issuer` каждого; совпадает ли issuer предыдущего с subject следующего.
- [ ] Срок действия leaf; SAN (какие имена покрыты).
- [ ] Key Usage / Extended Key Usage / Basic Constraints (`CA:TRUE`).
- [ ] Чем корневой отличается от промежуточного: где хранится, кто подписал, почему браузер доверяет цепочке.
- [ ] Что будет с `-servername wrong.example` (чужой SNI) — какой сертификат вернётся.

**Артефакт:** 3 строки цепочки + `Verify return code` + SAN + дата.

**Вывод (3–6 предложений):**

**Источник:** `man openssl-s_client`, `man openssl-x509`; RFC 5280; книга, 8.8.

## P5. `ss`: состояния и процессы

```bash
ss -tlnp
ss -tnp
ss -tanp state established
ss -s
ss -tlnp 'sport = :443'
```

**Что зафиксировать:**

- [ ] Колонки: State, Recv-Q/Send-Q, Local Address:Port, Peer Address:Port, Process.
- [ ] Кто слушает `0.0.0.0:22` / `127.0.0.1:...` — разница между всеми интерфейсами и loopback.
- [ ] `LISTEN`, `ESTAB`, `TIME-WAIT`: что означает каждое и кто создаёт.
